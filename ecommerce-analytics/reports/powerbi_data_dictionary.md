**Location:** `data/powerbi/` · **13 tables** · 335,188 rows · every table written as **both `.csv`

## Before you connect: four things that apply to every table

**1. The analysis base is already filtered.** Every table covers **delivered orders placed between
2017-01-01 and 2018-08-31**, keyed on `customer_unique_id`. Cancelled and undelivered orders, the
2016 pilot period and the truncated Sep–Oct 2018 tail are already excluded — do not re-filter for
them and do not expect totals to match the raw Kaggle files.

**2. There is no margin, cost or profit column anywhere — by necessity, not oversight.** The Olist
dataset contains no cost of goods, commission rate or fulfilment cost. Any margin field would have
to be fabricated. **`revenue` = item price only**; `freight` is a separate customer-paid cost and is
never added into revenue. Please do not build a "profit" measure from these tables.

**3. Use `is_truncated_period` on any time-series visual.** The source export thins sharply from
**2018-08-22** and stops on **2018-08-29** (daily order counts fall 251 → 11). This is the export
ending, not a demand collapse. `fact_orders.is_truncated_period` and `dim_date.is_truncated_period`
flag the affected days. **A monthly revenue chart that includes them will show a false cliff in
August.** Either filter them out or annotate the chart.

**4. Grain is stated for every table below.** Mixing grains without a proper relationship is the
fastest way to double-count revenue here — in particular, **do not sum `revenue` from both
`fact_orders` and `fact_order_items` in the same visual**.

### Suggested model

```
dim_date ──────────┐
                   ├──< fact_orders >── dim_customers_segmented
dim_region_perf.   │         │
dim_payment_perf.  │         └──< fact_order_items >── dim_product_performance
                   │                   │                 └── dim_category_performance
                   │                   └── dim_seller_performance
fact_revenue_forecast (standalone, by month)
fact_cohort_retention ── dim_cohort_summary
```

Relationships: `fact_orders[order_id]` 1—* `fact_order_items[order_id]`;
`fact_orders[customer_unique_id]` *—1 `dim_customers_segmented[customer_unique_id]`;
`fact_orders[order_date]` *—1 `dim_date[date]`.

# 6. `fact_cohort_retention` + `dim_cohort_summary`

**`fact_cohort_retention` grain: one row = one (cohort month × months since first purchase).**
207 rows · 5 columns. Long format — ready for a matrix visual with `cohort_month` on rows and
`months_since_first_purchase` on columns.

| Column | Description |
|---|---|
| `cohort_month` | Month of the customer's first purchase (`YYYY-MM`) |
| `months_since_first_purchase` | 0 = acquisition month |
| `retention_pct` | % of the cohort ordering in that month |
| `cohort_size` | Customers in the cohort |
| `retained_customers` | Count behind the percentage |

> ⚠️ **Set the colour scale to 0–1%, not 0–100%.** Month 0 is always 100%; **every later month is
> below ~1%**. On a default scale the entire heatmap renders as one flat colour. Consider excluding
> month 0 from the visual entirely.

**`dim_cohort_summary` grain: one row = one cohort month.** 20 rows · 7 columns.

| Column | Description |
|---|---|
| `cohort_month`, `new_customers`, `revenue`, `revenue_per_customer` | Cohort size and value |
| `months_observed` | **Use this.** Months between the cohort and the window close |
| `ever_repeated_pct` | % who ever ordered again — **do not compare across cohorts directly** |
| `repeat_rate_3mo_pct` | % repeating within 3 months — **the fair comparison** |

> ⚠️ **The most important caveat in this file.** `ever_repeated_pct` falls from 7.2% to 0.6% across
> cohorts, which looks like collapsing retention. It is **censoring**: that column correlates
> **r = 0.92** with `months_observed`. A January 2017 cohort had 19 months to return; an August 2018
> cohort had none. On the fair 3-month window, 2017 cohorts repeat at 0.978% and 2018 cohorts at
> 0.976% — **no decline at all.** Use `repeat_rate_3mo_pct` for any cross-cohort comparison, and
> only for cohorts with `months_observed >= 3`.

# 7. `fact_revenue_forecast` + `dim_forecast_model_comparison`

**`fact_revenue_forecast` grain: one row = one month.** 23 rows (20 actual + 3 forecast) · 8 columns
**Feeds:** Forecasting

| Column | Description |
|---|---|
| `period` | Month start date |
| `period_label` | `YYYY-MM` |
| `type` | `actual` or `forecast` |
| `actual` | Observed revenue (null for forecast rows) |
| `forecast` | Point forecast (null for actual rows) |
| `lower_95`, `upper_95` | 95% prediction interval (forecast rows only) |
| `value` | **`actual` where available, else `forecast`** — use this for one continuous line |

Build the chart as: `value` as a solid line, split styling on `type`, with `lower_95`–`upper_95` as
a shaded band.

> ⚠️ **Three caveats to surface on the forecast page.**
> 1. **The interval is wide — ±29% in month 1, ±44% by month 3.** That width is the honest output of
>    a 20-month series. Show the band; a bare point forecast would overstate confidence.
> 2. **No Black Friday.** Annual seasonality is not estimable from 20 months, so no seasonal model
>    was fitted. November 2017 ran **52% above October** and the forecast cannot reproduce it. Any
>    November projection will be far too low.
> 3. **The base is understated.** August 2018 is truncated, so the forecast starts low and is
>    conservative.

**`dim_forecast_model_comparison` grain: one row = one model.** 10 rows.
`model`, `MAE`, `RMSE`, `MAPE_pct`, `vs_naive_pct` (negative = better than naive). The winner is a
**3-month moving average** (MAE R$62,622, MAPE 7.13%, 31% better than naive); trend-extrapolating
models are 150–210% *worse* than naive.

# 8. Marketing proxy tables

> ⚠️ **These are NOT marketing channels and this is NOT attribution.** The dataset contains no
> campaigns, channels, ad spend, impressions, clicks or sessions. **CAC, ROAS, channel mix and
> conversion rate cannot be computed from any of these tables.** They describe *where and how demand
> converts*, never *where it came from*. Please label the dashboard page accordingly.

### `dim_region_performance` — one row per state (27 rows)
`customer_state`, `orders`, `customers`, `revenue`, `aov`, `avg_delivery_days`, `late_rate_pct`,
`avg_review_score`, `freight_pct_of_revenue`, `pct_of_revenue`.

Headline: São Paulo is 42% of orders with the **lowest AOV in the country (R$125.12)** but the best
service (8.7 days, 5.9% late, 4.25 stars). Bahia is the mirror image (19.3 days, 14.1% late, 3.93
stars, R$151.66 AOV).

### `dim_seller_performance` — one row per seller (2,945 rows)
`seller_id`, `revenue`, `items_sold`, `orders_n`, `products`, `avg_item_price`, `seller_state`,
`avg_delivery_days`, `late_rate_pct`, `avg_review_score`, `pct_of_revenue`,
`cumulative_pct_of_revenue`. Filter to sellers with 100+ orders before ranking service quality —
low-volume sellers produce unstable rates.

### `dim_payment_performance` — one row per payment method (4 rows)
`payment_type`, `orders_n`, `revenue`, `aov`, `median_value`, `avg_items`, `avg_review`,
`avg_installments`, `pct_of_orders`, `pct_of_revenue`. Credit card is 75.5% of orders and 78.9% of
revenue.

# Measure definitions to keep consistent

```
Total Revenue      = SUM(fact_orders[revenue])
Total Freight      = SUM(fact_orders[freight])          -- keep separate from revenue
Orders             = DISTINCTCOUNT(fact_orders[order_id])
Customers          = DISTINCTCOUNT(fact_orders[customer_unique_id])
AOV (mean)         = DIVIDE([Total Revenue], [Orders])
AOV (median)       = MEDIANX(fact_orders, fact_orders[revenue])   -- prefer this
Repeat Rate %      = DIVIDE(
                       CALCULATE(DISTINCTCOUNT(dim_customers_segmented[customer_unique_id]),
                                 dim_customers_segmented[is_repeat_customer] = TRUE()),
                       DISTINCTCOUNT(dim_customers_segmented[customer_unique_id]))
Late Rate %        = DIVIDE(CALCULATE([Orders], fact_orders[is_late] = TRUE()), [Orders])
Avg Review Score   = AVERAGEX(FILTER(fact_orders, NOT ISBLANK(fact_orders[review_score])),
                              fact_orders[review_score])
```

**On AOV:** order value is severely right-skewed (skew 9.9) and **70.8% of orders fall below the
mean**. Lead with the median (R$86.50) and show the mean (R$137.00) beside it, rather than
presenting the mean alone.

# Known caveats — summary

| # | Caveat | Affects |
|---|---|---|
| 1 | **No cost data → no margin or profit field exists** | All product/category visuals |
| 2 | **No marketing channel data → no attribution, CAC or ROAS** | Marketing page |
| 3 | **City names are normalised but not fully deduplicated** — accents and punctuation are fixed, genuine misspellings remain. **Use `customer_state` for geographic analysis, not city** | Maps |
| 4 | **`is_truncated_period` — data thins from 2018-08-22, stops 2018-08-29** | All trend visuals |
| 5 | **Cohort `ever_repeated_pct` is censored (r = 0.92 with observation time)** — use `repeat_rate_3mo_pct` | Cohort page |
| 6 | **Retention is near zero (<1% after month 0)** — set heatmap scale to 0–1% | Cohort page |
| 7 | **Forecast has no annual seasonality → no Black Friday** | Forecast page |
| 8 | **`review_score` is null for ~0.8% of orders** — exclude, do not treat as 0 | Satisfaction visuals |
| 9 | **`payment_type` is blank for 4 orders** with no recoverable payment record | Payment visuals |
| 10 | **All findings are observational** — no experiment exists in this data, so no causal claims | Every page |
| 11 | **Data ends August 2018** — historical, not current | Every page |
